# Review standard

规定代码与规格审查的职责、必查项与拒绝标准，避免「看起来绿」的合入。

## 1. 角色

| 角色 | 职责 |
| --- | --- |
| 实现者 | 按切片交付；自检清单；如实报告限制 |
| 协调者 | 拆分任务、集成、向用户确认未决项、组织审查 |
| 审查者 | 对照规格与规范检查行为、安全、测试与注释实质 |

实现者不得自审自合；涉及安全/停止/契约的变更须有独立审查意见。

## 2. 审查输入

- 任务简报与所属规格章节
- diff 与测试输出（含失败史，不只最终绿）
- 契约/生成物是否同步
- ADR 是否需要新增或更新
- 平台声明（是否触及 Darwin 停止范围、IPC、凭证等）

## 3. 必查清单

### 3.1 正确性与范围

- [ ] 实现未越出批准范围；未把局部闭环宣称为完整模块交付
- [ ] 失败关闭点与规格一致
- [ ] 无无关大重构混入

### 3.2 安全与授权

- [ ] Workspace / 角色校验完整
- [ ] 无密钥、token、明文凭证进入仓或日志
- [ ] Electron IPC / 上传路径 / 维护接口未引入后门

### 3.3 测试诚实性

- [ ] 存在可观察行为测试；关键负例存在
- [ ] 无 sleep、假报告、弱断言、缺夹具假绿
- [ ] 产品重试/UNSTABLE/停止 scope 语义未被测试配置扭曲

### 3.4 工程与注释

- [ ] 4 空格与工具链检查通过
- [ ] 中文注释实质合格（非灌水）；公开 API 已覆盖
- [ ] 日志英文且无敏感字段
- [ ] 锁文件与基线变更有理由

### 3.5 文档与契约

- [ ] Schema/OpenAPI/类型/样例一致
- [ ] 用户可见行为变更有文档或规格同步（若需要）

## 4. 明确拒绝标准

出现下列情形应拒绝或要求返工：

- 静默改变范围、架构、许可证或平台停止保证
- 将 Mac 受控停止证据表述为全后代排空
- AI 输出自动发布或测试依赖未授权真实 Provider
- 跳过钩子、强制推送主分支、提交密钥
- 以占位 UI / TODO 模块 / 默认 skip 声称功能完成
- 注释门禁靠粘贴口号「冲比例」

## 5. 审查结论写法

审查意见应区分：

- **阻断**：必须修复才能集成
- **重要**：应在合入前修复或获协调者书面延期
- **建议**：不阻断，记入后续

结论中禁止把「未跑」写成「已通过」。对平台相关声明，须写明证据来自哪类机器/架构。

## 6. 代理相关

- 子代理不负责最终合入裁决。
- 协调者不得用「合理默认」代替用户对未决架构/范围的确认。
- 审查发现规范冲突时，先停实现，升级文档或问用户。
