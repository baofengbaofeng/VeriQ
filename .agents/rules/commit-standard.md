# Commit Standard

规范 Git 提交的内容边界、消息格式与代理协作约束，保证历史可审阅、可回滚、可追溯。

## 1. 何时可以提交

- 行为变更须已有可观察测试证据（优先 RED → GREEN）。
- 相关聚焦测试已通过；移交集成前应跑与变更相关的更完整套件。
- 契约/类型/样例/文档在触及范围内已同步。
- 编码规范（注释、缩进、日志）已满足；不得把「稍后补注释」当作已知债默认带进主线，除非任务简报明确允许并记录跟踪项。
- 实现者默认**不 push**；由协调者决定何时推送与开 PR。

## 2. 提交内容边界

**允许：**

- 本任务归属的源码、测试、契约生成结果、必要文档与 ADR
- 与行为变更直接相关的锁文件更新（须说明原因）

**禁止提交：**

- 密钥、`.env`、凭证文件、设备 token、私钥、Cookie 库明文
- 本机状态：`.venv`、`node_modules`、本地 `build/` 产物、IDE 私有缓存、OS 垃圾文件
- 无关的格式化全库重排、与任务无关的驱动式重构
- 二进制发行包、浏览器下载缓存、未审批的大文件

共享工作区中其他任务的文件不得一并 stage。

## 3. 提交消息

### 3.1 结构

采用简短主题行 + 可选正文（与仓库既有风格保持一致；若仓库后续引入 Conventional Commits，以仓库配置为准）：

```text
<类型>(可选范围): <一句话说明为什么>

<可选正文：动机、风险、验证方式、关联任务/规格>
```

推荐类型：

| 类型 | 含义 |
| --- | --- |
| `feat` | 新能力 |
| `fix` | 缺陷修复 |
| `refactor` | 无行为意图变化的结构整理 |
| `test` | 仅测试 |
| `docs` | 仅文档 |
| `chore` | 构建/工具/杂项 |
| `perf` | 性能 |
| `revert` | 回滚 |

### 3.2 写作要求

- 主题行聚焦**为什么**，避免纯文件清单。
- 使用祈使语气或简洁陈述均可，但同一仓库内保持一致。
- 正文可写：失败关闭点、平台影响（如仅 Darwin）、验证命令摘要、未覆盖风险。
- 禁止在提交消息中粘贴密钥或完整用户数据。
- 一个逻辑变更一个提交；不要把无关修复塞进同一提交。

### 3.3 示例

```text
fix(runtime): 在租约过期时隔离未知 Worker 而非释放容量

过期 Attempt 若停止证明不确定，须保持隔离占用。
验证：pnpm --filter @veriq/runtime test 中相关 lease 用例。
```

## 4. Amend、钩子与强制推送

- 未经用户/协调者明确要求，不得 `--amend` 已推送提交，不得 `--force` 推送到主分支。
- 不得使用 `--no-verify` / `--no-gpg-sign` 跳过钩子，除非用户明确批准。
- 预提交钩子失败时：修复后打**新提交**，不要在失败状态下强行amend掩盖。

## 5. 分支与集成（代理）

- 实现子代理不创建远程分支策略、不 push、不合并。
- 协调者负责集成顺序、冲突裁决与 PR 描述中的测试计划。
- PR 描述须包含：变更摘要、测试计划勾选、已知限制；不得声称未跑过的验收已通过。

## 6. 检查清单

- [ ] 仅包含本任务文件；无密钥与机器状态
- [ ] 消息说明动机；必要时注明平台/规格影响
- [ ] 测试与契约同步已完成或在正文声明未覆盖项
- [ ] 未跳过钩子；未对主分支强制推送
