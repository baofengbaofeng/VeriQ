# Error handling and observability standard

行宽口径：源码及注释每个物理行最多 **120 个显示列**，与 IDE 的 120 列标尺一致。
中文及其它全角/宽字符占 2 列，ASCII 占 1 列；缩进、标点和注释分隔符均计入。
注释长度只统计有效正文的 Unicode 字符，不含缩进与注释符号。
独立单行及块注释首行有效正文为 40～120 字符；块注释续行不设 40 字符下限。

提升故障可诊断性与失败关闭一致性，避免静默失败和敏感信息泄漏。

## 1. 失败关闭优先

- 授权失败、契约校验失败、租约/fencing 失效、停止证明不确定、签名/信任根失败：必须失败关闭，禁止「尽量继续」。
- 部分成功须显式建模（保留业务结果、清理结果、证据完整性等独立事实），不得只留一个含糊的成功布尔值。
- 捕获异常后若无法安全恢复，应向上返回可分类错误，而不是吞掉后返回空成功。

## 2. 错误模型

- 对外 API：稳定的错误码 / 机器可读 `code` + 安全的人类可读说明；不暴露栈、SQL、本地路径、密钥。
- 对内领域：区分可重试瞬时错误与不可重试逻辑错误；未知业务副作用禁止盲目重放。
- 跨语言（Python ↔ TS ↔ 契约）错误码与结果枚举保持同一事实来源，禁止各端私自发明同义不同码。
- HTTP：未知 API 返回真实 404；认证失败与权限不足语义分离；维护接口对无权限调用不得冒充「无工作可做」。

## 3. 日志

- 日志 message 使用英文；结构化字段承载 ID、阶段、outcome、scope 等。
- 必带关联字段（按场景）：`workspace_id`、`run_id` / `job_id` / `attempt_id`、`runtime_id`、请求幂等键等——在已具备上下文时不得省略。
- 禁止记录：密码、token、Cookie、Authorization、连接串密钥、未脱敏隐私、离线包私钥材料。
- 同一失败路径须有且仅有清晰的主日志点，避免刷屏重复与完全无日志两种极端。
- 级别：`error` 表示需关注的失败；预期内负例（如权限拒绝）可用 `warning`/`info`，但须可检索。

## 4. 指标与健康

- 控制面提供真实健康检查：依赖（如 DB）失败不得报健康。
- 队列、租约回收、维护任务应能观测处理量、`hasMore`、失败计数；禁止只靠人工翻日志判断积压。
- 桌面/Agent 诊断信息可导出，但须脱敏且不自动上传密钥。

## 5. 用户与运维可见性

- UI/报告须区分：业务失败、清理失败、失联、取消、证据不全、停止未确认等，不得全部显示为「失败」。
- `UNSTABLE`、`INCOMPLETE`、`WORKER_LOST` 等 outcome 不得在展示层被折叠成普通 FAILED 而丢失语义。

## 6. 检查清单

- [ ] 新失败路径有明确码与英文日志，且脱敏
- [ ] 不确定状态进入隔离/失败关闭，而非假成功
- [ ] 跨语言错误/结果枚举已同步契约
- [ ] 关键运维路径可观测（计数或健康信号）
