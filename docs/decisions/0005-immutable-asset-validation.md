# ADR 0005 — Immutable asset validation and source identity

Status: accepted implementation boundary for T04; compiler, identity registry and verified Runtime completion remain subsequent tasks.

All eight resource kinds use the same draft revision, immutable version and successful Runtime receipt rules. A first catalog, dataset, fixture or environment cannot depend on a fabricated published CASE. `AssetSnapshotV1.validationTarget` identifies the candidate resource/version/revision and permits an empty `entryCaseVersionIds`. `CompiledAssetBundle.validationOnly: true` requires an empty entrypoint list but still requires actual files and pinned dependencies. Execution snapshots and TEST manifests pin `caseVersionId`; executable entrypoints explicitly map that version ID to a file path. Normal execution snapshots without a validation target and normal compiled bundles still require cases/entrypoints. T05/T09 must reject empty TEST selection and never report it as a passing run.

The service deterministically allocates the candidate UUID using UUIDv5/NAMESPACE_URL over `veriq:{workspaceId}:{resourceId}:{revision}:{documentHash}`. Publication adopts exactly that UUID. `documentHash`/version `sha256` hashes the complete `{kind, document}` envelope. `sourceHash` hashes RFC8785/JCS bytes of exactly `{schemaVersion, workspaceId, engineVersion, entryCaseVersionIds, assets}`. The service sorts assets by version UUID and entry case UUIDs lexically. Each asset includes resource/version IDs, kind, document and document-envelope SHA-256. The arrays' frozen ordering is part of identity; consumers must not reorder them. Validation target metadata, claimed source hash, job/run/attempt IDs, machine paths and execution values are excluded. Dropping validation metadata after publication preserves source identity. Exact retained manifest bytes remain the signing boundary.

Python uses `rfc8785==0.1.4`, Node/browser uses `canonicalize==2.1.0`, both Apache-2.0. Ordinary sorted Python JSON and JavaScript JSON.stringify differ on float formatting, negative zero and UTF-16 key sorting. Maintaining a custom JCS implementation would duplicate number/Unicode correctness and interoperability risk. The selected mature JCS implementations supply that behavior; the existing portable-JSON guard and a lone-surrogate check enforce their common input domain. Shared vectors cover numeric and Unicode boundaries and both languages verify the same source digest. The browser-facing package exports bytes and no Node crypto/Buffer dependency; callers choose their SHA-256 API. Lockfiles pin the packages, inventories record license metadata and release assembly must retain upstream license texts.

`GET .../resources/{resourceId}/validation-preview` produces the server-derived document hash, candidate version ID, closure source hash and engine version for the current revision. `POST .../validate` compares the submitted revision/hash to a fresh authoritative closure and persists immutable snapshot/manifest bytes plus a QUEUED VALIDATE job. This is the single `veriq_jobs` queue. It performs no compilation or artificial completion. All membership, mutation and publication checks occur in the existing installation-guard transaction order. ENVIRONMENT writes require MANAGE_ENVIRONMENT; kind is immutable.

Authentication adapter/credential references use `IdentityReferenceRegistry.require_role(session, scope, role)` rather than asset-version lookups. It must check adapter version, secretRef/version association, revocation, allowed identities and Workspace in the caller's transaction, returning no secrets. The default implementation rejects unresolved references. Drafts may retain structurally valid unresolved references; validation and publication cannot accept them. T07 supplies this registry.

A receipt asserts successful verified compilation by an approved **MANAGED** compiler Runtime and records runtime ID, completing attempt ID, engine version, source hash and exact compiled descriptor hash. Publication requires the retained finished job/active attempt, exact snapshot/manifest, matching root resource/revision/source, and every descriptor file's retained digest/length. **Matching hashes cannot establish that arbitrary executable code was produced by the approved compiler.** T08–T10's sole receipt writer must additionally authenticate current leases/fencing, confirm assigned Workspace/job/attempt/runtime, require an admin-approved trusted compiler with approved engine/compiler/SDK and dependency locks, validate the actual immutable artifacts and record successful completion atomically. A personal USER_REGISTERED token is insufficient. No production receipt writer or HTTP receipt creation route exists in T04; publication remains unavailable without that verified completion integration. Tests explicitly seed provenance and bytes at this unfinished boundary.

T12 must enforce the same provenance before redistributing executable compiled files and preserve exact bytes, signatures and lockfile integrity. It must not accept a caller-declared source hash as compiler attestation. T09 owns queue claims/leases/capacity/retry; this task introduces no secondary scheduler, lease loop or browser execution in the Python server.

Resource content is bounded at 2 MiB canonical UTF-8 bytes; create/draft HTTP envelopes at 2 MiB + 4096 bytes, other JSON operations at 64 KiB, and the Tornado HTTP transport at 3 MiB. Dependency closures are bounded at 1000 assets, depth 100 and 16 MiB canonical bytes. Binary streaming/retention remains T12. Lists use existing signed, actor/Workspace/filter-bound cursors with default 25 and maximum 100. Resource archival retains keys and immutable versions; restoring requires the same edit/environment permissions.

Verification on 2026-11-11: upstream metadata identifies rfc8785 0.1.4 (2024-09-27, Python >=3.8) and canonicalize 2.1.0 (2025-03-18); installed upstream LICENSE texts are Apache-2.0. The installed Python graph audit reports no known vulnerabilities across 62 packages. npm audit retains exactly the previously reviewed builder-only minimatch advisory GHSA-g3hv-75wg-m249 from [ADR 0003](0003-engineering-baseline.md); no new JCS package finding. The desktop builder caller/lock paths are unchanged, so its documented applicability assessment remains in effect. Audit absence is a point-in-time result, not a security guarantee.

Idempotent publication is also an artifact identity check: an existing revision must retain the same source/document/engine and the compiled descriptor hash bound by its original receipt. Revalidation with different compiled bytes returns409 rather than silently reusing or replacing the old executable artifact; identical bytes may return the same immutable version. Engine changes require saving a new draft revision before publication.
