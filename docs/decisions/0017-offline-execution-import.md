# 0017: Durable disconnected execution and separate result import authority

Approved by task coordinator, 2026-11-12. Offline execution uses the independently pinned Node24.22.1 runtime's built-in `node:sqlite` adapter (SQLite3.53.4, Node modules ABI137/NAPI10). No package/native addon graph changes. Node is MIT, SQLite public domain; Windows distribution uses the independent runtime rather than Electron's ABI. Windows packaging and native vault acceptance remain T20. The observed adapter invocation emitted no experimental warning.

A private SQLite database, with `veriq_` tables, WAL and FULL synchronous commits, owns the single local context across processes. The existing trusted worker, compiler entry, credential broker, SDK and native process supervisor remain execution authority. Unknown native stop evidence retains quarantine; neither elapsed time nor browser close releases ownership. Bundle signature, exact membership and bytes are rechecked and captured for every invocation.

Imported results use separate offline records, never online Attempt leases/fencing/capacity. Imported Runs have source OFFLINE_IMPORT and gate false. Declared device/trust/environment facts are retained separately from server verified bundle/current authorization facts. Web imports use current Cookie/CSRF Workspace EXECUTE plus nested download/draft permissions. Device imports use current authenticated enrollment and owner/share authority, not user-supplied IDs. Domain and header dedupe are immutable and reauthorized on replay. Bounded raw evidence transfer reuses private publication incarnations/fences; raw evidence stays privileged.

Migration0013 adds offline import/header-key/attempt/upload tables and makes publication ownership an exact XOR between the existing online upload FK and a Workspace-scoped offline upload FK. Existing online rows keep their original owner. Recovery and expiry consider both online and offline aliases before retiring an incarnation; empty physical fences remain durable. Downgrade refuses when offline import/upload history exists, rather than silently deleting reports or publication authority. Production rollback therefore requires retaining this schema or an explicit separately reviewed data-preservation procedure.

The existing bounded bundle-verification slots cover import archive verification. ZIP/signature work and raw File/S3 I/O occur outside the installation lock, followed by current-authorization and incarnation rechecks. A committed result freezes its exact artifact descriptors: pre-staged unlisted files stay inaccessible and late finalization cannot attach them. Only exact completed descriptor replays remain eligible, with current authorization.

Recovery claims the exact SQLite ownership state and generation atomically. A claimed unspawned owner cannot enter SPAWNING; a spawn that won the race requires native stop proof. Every stop, finish, event and checkpoint is fenced by that generation. SQLite schema version 2 adds this generation without discarding existing local history. Attempt handoff and the initial checkpoint commit together; ARTIFACT_CREATED and its scoped descriptor commit together after the raw file is flushed. Recovery preserves evidence and remains INCOMPLETE.

OfflineResultV1 may record strict executionChoices.browsers (one to three unique browsers); omission means the Chromium fallback. Signed SUITE entry browsers override this fallback, and signed role/dataset overrides remain authoritative. Runtime and importer derive the bounded matrix (at most 1000 variants) from signed CASE selection or the selected published/candidate SUITE. Import projects missing variants as INCOMPLETE CaseExecutions with zero attempts/events. A submitted passing prefix cannot erase unexecuted work. A complete factual matrix retains its factual outcome.

Published SUITE execution uses that SUITE's retained original source, immutable compiled descriptor/files and receipt; direct CASE uses its own retained compilation. DSL-only execution always uses exact draft/source.json. Published CASE dependencies retain their separate original source/receipt audit provenance and real published CASE IDs, even inside a candidate SUITE. No per-CASE receipt is presented as proof of a different SUITE compilation. DSL-only imported facts remain conservative because the export carries no independently verified compiled expected plan for the candidate.

Legacy results without execution facts are accepted conservatively only when the signed selection and permitted fallback identify exactly one variant for that CASE. Ambiguous legacy attribution returns OFFLINE_VARIANT_FACTS_REQUIRED (422). The host keeps local history and pending upload; it never reruns business operations to repair an import. This explicit pre-release compatibility boundary avoids inventing variant attribution.
