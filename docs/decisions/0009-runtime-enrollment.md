# ADR 0009: Runtime ownership, enrollment and current authorization

Status: accepted for T08, including the coordinator-approved dependency reconciliation with T16.

A Runtime is owned by exactly one real USER or SERVICE_ACCOUNT. Ownership, Workspace binding, explicit owner consent, location, current trust and device-reported capabilities are separate facts. Registration records OFFLINE; it does not create a worker, lease, heartbeat or historical Run. Capabilities cannot approve compiler/SDK releases. MANAGED_CLOUD never grants MANAGED trust.

Human enrollment uses a 12-character base32 approval code (60 random bits) and a separate 256-bit device polling secret. Both expire after ten minutes and only hashes are stored. The authenticated owner inspects the requested name/capabilities, selects their current Workspace and consents to private, named-member or whole-Workspace sharing. Only the polling secret can consume an approval once and receive a device credential. Native endpoints do not accept Cookie identity; human approval retains the existing Origin and CSRF protections. Request creation is bounded per source over the expiry window, and clients poll at a five-second interval. Enrollment codes and credentials are never carried in URLs.

Device tokens are 256-bit secrets, hash-only at rest, bound to one Runtime and Workspace, expire after 24 hours, and are independently revocable. Rotation issues one replacement and invalidates its predecessor atomically. Responses are no-store. Ownership and current user/membership or service-account authorization are rechecked on device authentication and dispatch policy. Mutation and authorization transactions acquire the existing installation guard before mutable identity/Workspace reads, preserving account-disable and membership-revocation ordering. T09 must retain this guard ordering through actual assignment, lease/fence, grant and credential checks; T08 does not implement a fake claim endpoint. T10 owns unattended renewal, recovery from lost rotation responses and worker lifecycle.

The reusable service-account foundation is brought forward from T16: `veriq_service_accounts` is Workspace-scoped and `veriq_service_tokens` records purpose, expiry, consumption and revocation. Current Workspace OWNER/ADMIN can create/list/disable accounts and issue ten-minute single-use `RUNTIME_ENROLLMENT` tokens. This purpose gives no trigger, maintenance or credential permission. Cloud enrollment consumes that secret into a service-owned Runtime in the same Workspace. Current Workspace OWNER/ADMIN manages service-account consent; a global administrator without membership gains no project access. T16 extends these exact identities and purpose-bound tokens rather than introducing a second identity model.

Only a system administrator with current access to the bound Workspace can grant MANAGED, within existing explicit owner sharing consent. Credential delivery separately requires current Workspace OWNER/ADMIN (MANAGE_ENVIRONMENT). The system administrator may be a Workspace VIEWER/EDITOR and approve hardware trust, but cannot authorize delivery of that Workspace’s secrets. A non-global Workspace OWNER/ADMIN can grant delivery after separate MANAGED approval and owner consent through PUT `/api/v1/workspaces/{workspaceId}/runtimes/{runtimeId}/credential-delivery` with `{allowCredentialDelivery:boolean}`. The combined trust update may enable delivery only if the actor also has MANAGE_ENVIRONMENT; system security demotion may always clear it. Any consent change resets trust and credential delivery approval; private consent never authorizes administrators to dispatch. Revocation prevents new device operations; historical outcomes are not rewritten. T09/T11 separately retain gateAtExecution and evaluate gateNow from current trust; T08 creates no synthetic historical results.

DeviceCredentialsDTO preserves `runnerId` and adds the approved initial `workspaceId`. `issuerId` and `trustedKeys` are optional as a pair until T14 provides a real Ed25519 bundle issuer. T08 omits both. Bundle verification must fail clearly without a trusted issuer; T14 must deliver actual roots via the authenticated bound control origin or approved out-of-band provisioning, never via a downloaded bundle trusting itself.

Node development stores local device configuration in a private directory/file under env-paths, with proper-lockfile serialization. This is an explicit development seam, not a claim of an OS credential vault. T20 supplies native packaging and OS-vault storage. CLI secrets enter via bounded stdin or private configuration and never argv. Doctor inspects the actual Node/OS/architecture, engine packages, browser executable and launch, and configured server reachability. It reports failures with exit codes and sanitized diagnostics. The control service has no Node or browser runtime dependency.
