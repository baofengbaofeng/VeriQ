## 需求与统一口径

本次按用户明确要求修复整个项目的源码，而非只修新增代码。
每个物理行最多 120 个显示列，与 IDE 的等宽字体 120 列标尺一致。
中文及 Unicode W/F 宽字符占 2 列，普通窄字符占 1 列，Mn/Me/Cf 不另占列。
缩进、标点、引号和注释前缀均计入；Tab 前进至下一个 4 列制表位，仍禁止用 Tab 缩进源码。
不得使用 `len()`、UTF-8 字节数、JavaScript `length` 或编辑器软换行替代这个判定。

规则详见 [编码规范总则](../../.agents/rules/coding-standard.md#11-显示列宽的统一计算)。
`AGENTS.md`、规则目录中全部专项规则及两份语言指南均已同步澄清。
导入和生成源码也执行同一上限；长字符串须保持运行时内容，不得引入意外的换行或空白。

## 防止问题再次出现

```bash
python3 scripts/line_width.py
# 或在具备仓库 Python 工具链时运行：
pnpm lint:width
```

根 `pnpm lint` 已调用显示列宽检查，既有服务端发行流程调用它时会执行同一门禁。
检查器通过真实 Git 索引枚举已跟踪与未忽略的新源码，不排除生成类型、测试或旧代码。
范围包括 Python、TS/JS、C/C++、Objective-C++、Java、Shell、HTML/CSS、安装与部署源码。
它只报告路径、行号和列数，不回显源码正文。
Unicode 分隔字符不会把同一物理行拆成多个受检行。

契约生成器使用固定 Unicode 15.0 宽字符数据与 TypeScript 词法扫描拆行，保持原类型语义。
桌面操作类型生成器直接产生多行类型声明；两类生成源码都已通过正式生成入口更新。
未添加第三方依赖，也未变更依赖锁、产品契约、浏览器版本或平台能力。

注释首行至少 40 个 Unicode 字符与整行最多 120 个显示列是独立要求，必须同时满足。
审计器残留的旧 60 字符门槛已同步到基线规则的 40 字符；覆盖率仍严格大于 40%，排除清单未改变。
这次换行修复不代表已有的全仓注释覆盖率和注释质量债务已经解决。
