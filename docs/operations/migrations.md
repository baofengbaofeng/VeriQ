# VeriQ 数据库迁移

单实例开发可显式执行迁移。多实例生产应使用与待部署 API 相同版本、同一受保护配置的独立迁移 job，在迁移成功退出后再切换 API 实例。API 的 `serve` 不自动执行迁移。

```sh
veriq_server --config /etc/veriq/veriq.json migrate
```

配置路径是示例；操作员应使用实际受保护配置。命令沿用既有配置优先级及密钥，不生成或替换密钥，也不修改配置文件。迁移失败会返回非零退出码，部署流程必须停止切换并检查数据库与迁移状态。

迁移只接受 MySQL 8.4。入口从实际连接查询逻辑数据库名，将其 UTF-8 SHA-256 前 48 位十六进制加上 `veriq_migrate_` 前缀，形成 62 字符命名锁。连接地址写法或密码不同、实际选中同一数据库的调用竞争同一锁；不同数据库独立。无法确定数据库名时拒绝迁移，错误消息不输出数据库名或连接凭据。

持锁、执行 Alembic `upgrade head`、提交与显式释放均使用同一物理数据库连接。普通事务提交不会释放 MySQL 命名锁。锁由同一 MySQL 服务管理，只约束使用该入口的迁移调用；操作员直接执行的 SQL 不受该入口互斥保护。

默认最多等待锁 60 秒。`GET_LOCK` 超时会产生 `MIGRATION_LOCK_BUSY`，该次调用不执行升级。Python 调用方可使用 `await migrate(settings, lock_timeout_seconds=0)` 立即拒绝忙锁，也可传入 0 至 60 的整数等待秒数；布尔值、非整数及越界参数在访问数据库前被拒绝。现有 CLI 使用默认等待值，没有新增超时命令行参数，也没有内部定时任务或自动重试。

取得锁的结果未知时产生 `MIGRATION_LOCK_ACQUIRE_UNCONFIRMED`。升级和提交成功后仍须明确验证释放返回成功；释放失败、结果未知、原连接失效或原物理 session 被替换时产生 `MIGRATION_LOCK_RELEASE_UNCONFIRMED`，禁止据此继续切换。首个升级或取消异常保持原样，清理问题仅附加固定非敏感状态。

取消或断开客户端连接不等于 MySQL 立即结束当前查询。服务端可能继续执行当前语句并暂时保持原锁；入口会清理连接并报告失败或释放未知，不会借新连接假称原锁已释放。遇到这种状态，应由操作员确认原迁移任务和数据库 session 已结束、锁已不再占用，再检查 Alembic 版本及应用数据，决定是否重新执行独立迁移 job。不要绕过锁直接启动后续升级。

升级前应按已有运维流程备份数据库、制品及解密或验签所需密钥，并确认备份可恢复。MySQL DDL 可能已提交，迁移失败或取消不保证所有变更回滚；不要自动降级或删除用户 schema。恢复应采用已审阅的备份恢复或向前修复流程，二进制回滚还需先确认当前数据库兼容。

此入口互斥组件不代表完整 T21 运维交付：生产 job 装配、readiness、备份恢复工具、兼容矩阵及各平台部署验收仍需分别完成。
