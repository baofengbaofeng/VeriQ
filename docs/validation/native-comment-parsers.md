# Native comment parsers

状态：预检完成，计量与编译门禁的职责边界待用户选择。日期：2026-11-18（Asia/Shanghai）。
本记录不批准新依赖、不改变现行计量规则，也不使任何原生文件获得计量资格。

## 当前结论

VeriQ 需要可信地识别 C、C++、Objective-C++ 的真实注释，避免把字符串中的标记算成注释，
同时覆盖宏替换体及不活跃条件分支。现有两个候选入口各有实测缺口，不能直接接入正式门禁。

| 检查对象               | 实测结果                                                                               | 能得出的结论                                                      |
| ---------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| tree-sitter C/C++      | 21 个原始文件中，整树与坐标检查通过 14 个、拒绝 7 个；通过者中 10 个含不透明预处理参数 | 无语法树错误不足以证明注释范围完整；另外 4 个也未独立证明完整性   |
| tree-sitter 合成输入   | 12/26 符合预期；C 和 C++ 的宏行注释均被吞入预处理参数，根节点未报错                    | 不能只遍历 `comment` 节点计量                                     |
| 系统 Clang 19 原始词元 | 25/25 个主文件可读取范围，共 429 个候选 COMMENT；25 个均因缺失头文件产生 fatal         | 范围可读不等于整文件语法合格，也未独立逐段证明 429 个范围的完整性 |

Clang 预检没有编译或执行 VeriQ 原生代码，也没有加入假 SDK、改写条件分支或屏蔽诊断。
不活跃分支内的非法函数没有诊断，不能据此认定 Clang 对有效预处理程序的行为错误；
本项目关注的是整份源文件的注释边界，不能仅靠当前活跃分支的编译结果证明全部边界。

## 可复核的关键输入

以下为已实际运行的短输入，不是建议添加到业务源码中的开发注释。

```c
#define X 1 // 宏内真实行说明
```

固定 C/C++ grammar 均返回 `root.has_error=false`、零个注释节点，
而预处理参数的原始内容为 `1 // 宏内真实行说明`。因此现有树适配入口会漏计真实注释。

Clang 的配对实验保留相同的坏输入，仅在前方添加一个不存在的头文件引用：
未闭合普通字符串、未闭合 C++ raw string、非法函数语法、非法 UTF-8、NUL、未知字符及未闭合块注释。
共 13 对覆盖 C/C++ 的适用组合；加入缺失头后，后部诊断均消失。
部分输入仍通过字节范围覆盖检查，故不能只凭词元种类、覆盖缺口或 TU 返回成功判断整文件有效。

## 需要确认的门禁边界

这里的“词法检查”回答哪里是真注释、字符串和代码；“平台编译”回答源码在对应 SDK、宏和编译参数下是否可编译。
两项都需要，待选择的是平台编译证据是否为原生计量资格的前提。
方案 B 也可以分别执行再汇集，但缺少对应编译证据时不能确认完整计量。

| 对比项           | A：独立词法计量，平台编译另设强制门禁（建议）                                        | B：计量须绑定完整目标平台编译上下文                                                        |
| ---------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| 注释资格         | 由成熟词法器提供完整原始范围及可靠的词法失败信号；不承担完整语义编译                 | 需要原始范围证明，并结合实际 SDK、编译参数和正确包含上下文验证；头文件也需明确所属翻译单元 |
| 缺失平台 SDK     | 词法审计不得因缺 SDK 假通过或漏计；独立词法路径验证合格后可不依赖 SDK                | 对应目标的计量证据保持阻断，须从目标环境取得合格结果                                       |
| 平台编译         | Mac Intel、Mac ARM、Windows、Linux 分别执行，仍是完整 MVP/发行的必要条件             | 同样分别执行，并将对应证据作为原生计量资格的前提                                           |
| Linux 开发机反馈 | 独立词法路径验证合格后，可给出所有原生文件的注释审计结果；不能据此宣布跨平台编译通过 | 本机缺少其他平台上下文时，完整计量需等待跨平台证据汇集                                     |
| 条件分支         | 词法范围须覆盖原始文件各分支，不按当前活跃分支删减                                   | 编译验证仍须明确配置覆盖；还需独立证明非活跃分支的原始注释范围                             |
| 工程代价         | 新增可信词法适配与独立门禁职责；现有 `TU/get_tokens` 结果尚不足以实现                | 新增编译上下文、目标证据绑定与汇集；本地一条审计命令不再天然自包含                         |
| 主要限制         | 必须实证未闭合字符串/注释、原始字符串、续行、坏字节等错误不会被吞掉                  | 目标环境、宏、SDK 或输入身份不完整即阻断；成功编译单独也不能证明全部注释范围               |

协调者建议 A：将注释完整性与平台可编译性分成明确的强制检查，便于本地开发，
也避免为计算注释比例要求 Linux 控制服务构建机同时具备 Apple 和 Windows SDK。
这是职责边界建议，不是已有实现或已获批准的依赖选型。

### 两种方案共同保留的要求

- 全仓有效注释行 /（注释行 + 非空代码行）严格大于 40%，不排除原生代码、不设逐文件配额。
- 中文说明、首行正文 40～120 个 Unicode 字符、物理行最多 120 显示列及公开 API/关键逻辑说明要求不变。
- 字符串伪标记、宏、条件分支、Objective-C++ 混用语法必须有实际正反例；语言不能只按扩展名猜测。
- 原始 UTF-8、字节范围、物理行和码点坐标需核验；未知输入、解析器不可用、版本/ABI 漂移均失败关闭。
- 不用正则或自写通用 lexer 补齐成熟工具的缺口，不伪造 SDK，不删除预处理源码，不静默吞诊断。
- 工具与生产依赖闭包分离；版本、许可、供应来源、目标平台加载和安全证据须在正式接入前落地。
- 选择 A 后也不能直接采用本次 `TU/get_tokens` 实验；可靠的独立词法失败信号尚未证明。
- 选择 B 后也不能只上传一个“编译通过”标志；证据需绑定源码、目标、实际工具链、参数和依赖输入。
